# Bicep pipelines

Generated by Skyforge. **Nothing here has ever been run**, on a pipeline service or against Azure, so try it on a non-production subscription first.

## What the pipelines do

Deployments run in this order: `tenant.bicep`, then `main.bicep`. Each one is validated and previewed only after the one before it has been deployed.

- `tenant.bicep` deploys at tenant scope; `main.bicep` deploys at management group scope, using its `.bicepparam` file.
- A pull request that touches this folder runs validate and what-if. Later deployments can fail here on a first run, because what they read does not exist yet.
- A manual run with `action` set to `apply` runs what-if, waits for approval, then deploys. A deployment what-if finds no changes for skips the deploy.
- The deploy runs what-if again and stops if the changes differ from the ones that were reviewed. What-if can report changes that a deployment would not make, so it is a review aid and not a guarantee.

## Variables

Set these as pipeline variables: GitHub environment variables, or the Azure DevOps variable group. Leave any row marked optional unset if it does not apply.

| Variable | Used for | Needed |
|---|---|---|
| `AZURE_MANAGEMENT_GROUP_ID` | Management group to deploy `main.bicep` from. Every subscription in this package must sit below it | Required |
| `AZ_SUBSCRIPTION_APP_DEV` | Subscription ID left blank at intake (tenant.bicep, main.bicep) | Required |
| `AZ_SUBSCRIPTION_MANAGEMENT` | Subscription ID left blank at intake (tenant.bicep, main.bicep) | Required |
| `AZ_SUBSCRIPTION_CONNECTIVITY` | Subscription ID left blank at intake (tenant.bicep, main.bicep) | Required |
| `AZ_SUBSCRIPTION_IDENTITY` | Subscription ID left blank at intake (tenant.bicep, main.bicep) | Required |
| `VPN_SHARED_KEYS` | Secure parameter `vpnSharedKeys` (main.bicep). **Store as a secret**, as a JSON object | Optional |
| `AZURE_TENANT_ID` | Microsoft Entra tenant ID. GitHub only | Required on GitHub |
| `AZURE_TENANT_PLAN_CLIENT_ID` | Client ID of the identity for what-if (tenant). GitHub only | Required on GitHub |
| `AZURE_TENANT_APPLY_CLIENT_ID` | Client ID of the identity for deploy (tenant). GitHub only | Required on GitHub |

## Identities

No cloud keys are stored. Each deployment has two identities, and the difference between them matters:

- **Plan** runs validate and what-if. A pull request from this repository can change the pipeline and use this identity, so it gets read access to resources. It also needs the deployment actions below.
- **Apply** can change resources, and only the protected apply gate can use it.

Each deployment signs in once, so one identity pair covers every subscription in the package. You do not need one identity per subscription. Grant these roles, and nothing wider:

- `tenant.bicep` plan: Management Group Reader at the tenant root (`/`), and a custom role with `Microsoft.Resources/deployments/*` there.
- `tenant.bicep` apply: Owner or Management Group Contributor at the tenant root (`/`), and Owner on each subscription it moves. Keep this identity apart from the workload ones: it can reorganise the tenant.
- `main.bicep` plan: Reader, and a custom role with `Microsoft.Resources/deployments/*`, on `AZURE_MANAGEMENT_GROUP_ID`, which subscriptions below it inherit. Deployment actions alone change nothing, and validate and what-if check this identity for read access only.
- `main.bicep` apply: on the same management group, or on each subscription and the deployment scope, the rights to create what this package creates, usually Contributor plus Role Based Access Control Administrator.

## GitHub Actions

1. Copy `pipelines/github-actions.yml` to `.github/workflows/bicep-azure-tom-homelab-dev-tom-homelab.yml`. GitHub runs workflows only from that folder.
2. Create environments `bicep-azure-tom-homelab-dev-tom-homelab-plan` and `bicep-azure-tom-homelab-dev-tom-homelab-apply` **before the first run**. GitHub otherwise creates them unprotected. Add required reviewers to the apply environment, limit it to the default branch, and set the variables on both.
3. For each identity, create a Microsoft Entra app registration or a user-assigned managed identity. Give it a federated credential with issuer `https://token.actions.githubusercontent.com`, audience `api://AzureADTokenExchange` and only its own subject: `repo:<owner>/<repo>:environment:bicep-azure-tom-homelab-dev-tom-homelab-plan` or `-apply`. Add no client secret.

## Azure DevOps

1. Create the variable group `bicep-azure-tom-homelab-dev-tom-homelab`, and mark any secret variable as secret.
2. Create the environment `bicep-azure-tom-homelab-dev-tom-homelab-apply` with an approval **before the first run**. Azure DevOps otherwise creates it with no checks.
3. Create Azure Resource Manager service connections using workload identity federation, with these exact names: `azure-tom-homelab-dev-tom-homelab-tenant-plan`, `azure-tom-homelab-dev-tom-homelab-tenant-apply`, `azure-tom-homelab-dev-tom-homelab-workload-plan`, `azure-tom-homelab-dev-tom-homelab-workload-apply`. Use one identity per connection, with only the roles listed above, so no connection holds a client secret.
4. Add approval and branch checks to the apply connections, and allow only this pipeline to use them. Then create the pipeline from `customers/tom-homelab/dev/tom-homelab/pipelines/azure-pipelines.yml`. Azure Repos ignores the file's `pr` section, so add a build validation branch policy for pull request plans.

A deployment that outlasts its sign-in, usually about an hour, keeps running in Azure while the pipeline step fails. If that happens, check the deployment in the Azure portal, then run the pipeline again.
